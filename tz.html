Техническое задание на разработку портала ВНИИКП (боевая версия)

Заказчик: ВНИИ кондитерской промышленности — филиал ФГБНУ «ФНЦ пищевых систем им. В. М. Горбатова» РАН Объект: публичный сайт + система управления (back-office) с личными кабинетами и онлайн-монетизацией Основание: утверждённый прототип (папка wniikp-prototype/), показанный руководству Статус документа: редакция 1 от 07.06.2026 · согласуется с институтом

1. Назначение и цели

Создать боевую версию портала института, который:

  1. представляет институт и его услуги (испытания, экспертиза, КТ-контроль, обучение, издания);
  2. приносит доход — принимает заявки и оплату за услуги, обучение и платные издания;
  3. управляется сотрудниками через личные кабинеты с разграничением прав (RBAC);
  4. обеспечивает финансовую прозрачность для контролирующих органов (Счётная палата, учредитель);
  5. соответствует законодательству РФ (152-ФЗ о ПДн, доступность ГОСТ Р 52872, локализация данных в РФ).

Прототип фиксирует дизайн-систему, структуру и сценарии. Боевая версия добавляет бэкенд, БД, авторизацию, оплату и интеграции.

2. Термины

  • Заявка (лид) — обращение клиента с сайта.
  • РИД / приносящая доход деятельность — платные услуги бюджетного учреждения.
  • КОСГУ 130 — код доходов от оказания платных услуг.
  • План ФХД — план финансово-хозяйственной деятельности.
  • RBAC — ролевая модель доступа.
  • RAG — генерация ответов ИИ с опорой на базу знаний института.

3. Состав системы

  1. Публичный сайт (витрина, заявки, библиотека, ИИ-консультант, праздничный баннер, доступность, SEO).
  2. Back-office (личные кабинеты по ролям).
  3. Сквозные сервисы: авторизация, файловое хранилище, платежи, ИИ, уведомления, аудит, конфигурация.

Дизайн-система, вёрстка, иконочный набор, тексты и структура берутся из прототипа (переиспользовать styles.css, компоненты app.js, сценарии admin.js, контент-конфиг site.json, праздники holidays.json).

4. Функциональные требования — публичный сайт

4.1 Контент-страницы

Главная, Об институте, Услуги, Решения для бизнеса, КТ-контроль, Обучение, Библиотека, Новости, Кейсы, Политика конфиденциальности, страница услуги (эталон). Контент редактируется в админке, без участия программиста (см. 5.7).

4.2 Заявки (лиды)

  • Формы на страницах (услуга, обучение, общая) с обязательным согласием на обработку ПДн (152-ФЗ) и ссылкой на политику.
  • Отправка → запись в БД → попадание в воронку кабинета менеджера → уведомление ответственному (e-mail/мессенджер).
  • Антиспам (капча/honeypot/rate-limit). Подтверждение пользователю (экран «Заявка отправлена»).
  • Опционально — синхронизация с CRM (Bitrix24) института.

4.3 Электронная библиотека

  • Каталог изданий: бесплатные (свободное скачивание) и платные.
  • Платное издание выдаётся только после оплаты (см. 6): защищённая ссылка с ограниченным сроком/числом скачиваний; запрет прямого доступа к файлу.
  • Метаданные: название, авторы, год, тип, размер, цена, обложка, файл, статус (опубликовано/черновик).
  • Учёт продаж изданий как доход (КОСГУ 130).

4.4 ИИ-консультант

  • Виджет-чат на всех страницах.
  • Ответы через российскую LLM (YandexGPT или GigaChat) + RAG по базе знаний института (услуги, ГОСТ, библиотека, цены, кейсы, контакты).
  • Ограничители: отвечает только по тематике института; не выдумывает цены/аккредитацию; при неуверенности — предлагает оставить заявку.
  • Передача «горячих» диалогов менеджеру (создание лида из чата), логирование диалогов, согласие на обработку ПДн.

4.5 Праздничный баннер отрасли

  • Автопоявление в даты профильных праздников; источник — конфиг (аналог holidays.json), управляется в админке (см. 5.8).
  • Поддержка фиксированных и вычисляемых дат (например, 3-е воскресенье октября), своей иконки, кнопки-CTA, вкл/выкл, порядка.

4.6 Доступность и SEO

  • Версия для слабовидящих по ГОСТ Р 52872 (размеры шрифта, цветовые схемы, изображения вкл/выкл, сохранение настроек).
  • Соответствие WCAG 2.1 AA (контраст ≥ 4.5:1).
  • SEO: семантическая разметка, Open Graph/Twitter, JSON-LD (Organization, BreadcrumbList, Course), canonical, sitemap.xml, robots.txt, человекопонятные URL.

5. Функциональные требования — личные кабинеты (RBAC)

5.1 Директор

Дашборд: выручка, число заявок, конверсия, загрузка лабораторий; графики (по месяцам, по услугам); последние заявки (просмотр). Доступ ко всем разделам в режиме чтения + отчёты.

5.2 Менеджер (отдел продаж)

Воронка продаж (канбан: Новая → В работе → Счёт выставлен → Оплачено → Выполнено). Карточка заявки: переписка с клиентом, выставление счёта, фиксация оплаты, формирование акта, передача задания в лабораторию, создание заявки вручную. Уведомления о новых заявках.

5.3 Бухгалтерия

Выручка, счета и оплаты, динамика. Отчёт для контроля (Счётная палата/учредитель): доходы по КОСГУ 130, исполнение плана ФХД (план/факт), реестр «договор → счёт → акт → поступление», контроль полноты первички, аудиторский след. Выгрузки: CSV, данные для формы 0503737, выгрузка в 1С.

5.4 Руководитель лаборатории

Все задания на испытания, распределение по сотрудникам, загрузка протоколов, аналитика загрузки.

5.5 Научный сотрудник (с уровнями доступа)

Только свои задания; ввод результатов и протоколов; КТ-задания открывают расчётный КТ-модуль. Разграничение: рук. лаборатории видит всё, сотрудник — только своё.

5.6 Техподдержка

Тикеты (приём, ответ, закрытие), управление контентом сайта, управление праздниками.

5.7 Управление контентом

Редактирование разделов сайта (новости, услуги, обучение, кейсы, реквизиты) через визуальный редактор; публикация без участия программиста; версионирование/черновики.

5.8 Администратор

Пользователи и роли, матрица доступа (RBAC) с возможностью редактирования прав, все модули, журнал аудита, конфигурация системы, управление праздниками и библиотекой.

5.9 Сквозной аудит

Все значимые действия (смена статуса заявки, выставление счёта, правка контента, изменение прав) пишутся в журнал аудита (кто, что, когда) — для внутреннего контроля и проверок.

6. Монетизация и оплата

Особенности бюджетного учреждения (ФГБНУ):

  • Поступления зачисляются на лицевой счёт в Казначействе, не на обычный расчётный счёт.
  • Эквайринг и его закупка регулируются (44-ФЗ); интеграция с ГИС ГМП для учёта платежей в бюджет.
  • Доходы — приносящая доход деятельность, учёт по КОСГУ 130, расходование строго по уставу.

Требования:

  • Подключение платёжного провайдера (ЮKassa / CloudPayments / иной, согласованный с бухгалтерией) с зачислением на лицевой счёт.
  • Сценарий: заявка/издание → счёт → онлайн-оплата → подтверждение → выдача результата/файла → формирование первичных документов.
  • Фискализация (54-ФЗ) при необходимости; квитанции/чеки клиенту.
  • Платёжные реквизиты и ключи подключает институт (договор с провайдером); разработчик реализует интеграцию.

7. Финансовая отчётность и контроль

  • Реестр доходов от платных услуг (КОСГУ 130) с документным следом: договор → счёт → акт → поступление.
  • Сверка «план ФХД ↔ факт», контроль полноты первичных документов.
  • Подготовка операционных данных для формы 0503737 (приказ Минфина № 33н) и выгрузка в бухгалтерскую программу (1С).
  • Хранение аудиторского следа изменений. Бухгалтерские проводки и официальная отчётность — в 1С; портал отдаёт сверочные данные.

8. Нефункциональные требования

  • 152-ФЗ: согласия на обработку ПДн, политика, минимизация и защита данных, право на отзыв/удаление, реестр согласий.
  • Локализация данных: серверы и хранилище — на территории РФ.
  • Доступность: ГОСТ Р 52872, WCAG 2.1 AA.
  • Безопасность: HTTPS, хранение паролей (bcrypt/argon2), защита от XSS/CSRF/SQLi, ограничение доступа к платным файлам, rate-limiting, журналирование, регулярные бэкапы и план восстановления.
  • Производительность: время ответа страниц < 1.5 c при штатной нагрузке; кеширование.
  • Совместимость: актуальные браузеры, адаптив (mobile-first), корректная печать.
  • Надёжность: мониторинг доступности, оповещения об инцидентах.

9. Рекомендуемая архитектура и стек

Рекомендация согласована со стеком, уже используемым заказчиком (Django/PostgreSQL/Redis), для единообразия сопровождения.
  • Backend: Python 3 + Django + Django REST Framework.
  • БД: PostgreSQL (+ расширение pgvector для RAG-индекса ИИ-консультанта).
  • Кеш/очереди: Redis + Celery (фоновые задачи: уведомления, выдача файлов, синхронизации).
  • Frontend: серверный рендеринг Django-шаблонов с переиспользованием дизайн-системы прототипа (либо лёгкий SPA — по согласованию). Виджеты (консультант, баннер, доступность) — на текущем ванильном JS.
  • Файловое хранилище: S3-совместимое объектное хранилище в РФ (Yandex Object Storage / VK Cloud).
  • LLM: YandexGPT (Yandex Cloud) или GigaChat (Сбер) — оплата по договору, данные в РФ.
  • Хостинг: инфраструктура в РФ; CI/CD, staging + production.

10. Интеграции

  1. Платёжный провайдер (эквайринг) + ГИС ГМП.
  2. 1С / бухгалтерская программа — выгрузка доходов, счетов, актов.
  3. LLM-провайдер (YandexGPT/GigaChat) — ИИ-консультант.
  4. CRM (Bitrix24) — опциональная синхронизация заявок.
  5. E-mail / SMS / мессенджер — уведомления клиентам и сотрудникам.
  6. Аналитика (Яндекс.Метрика) — поведение и конверсии.

11. Модель данных (основные сущности)

  • User / Role / Permission — сотрудники, роли, права (RBAC).
  • Lead — заявка (клиент, услуга, сумма, статус, менеджер, переписка).
  • Invoice / Payment / Act — счёт, оплата, акт (связь с Lead, КОСГУ).
  • LabTask / Protocol — задание на испытание, исполнитель, протокол, статус.
  • Publication / Order / Download — издание, заказ, выдача файла.
  • Holiday — праздник (дата/вычисляемая, иконка, текст, CTA, вкл/выкл, порядок).
  • Ticket — обращение в техподдержку.
  • ContentBlock / Page — редактируемый контент.
  • AuditLog — журнал действий.
  • Consent — согласия на обработку ПДн.

12. Перенос из прототипа

Переиспользуется без переработки: дизайн-токены и стили (styles.css), иконочный SVG-набор, компоненты витрины (app.js), сценарии и UX кабинетов (admin.js), контент-конфиг (site.json), праздники (holidays.json), КТ-модуль (ct-analyzer.html), тексты, структура и SEO-разметка. Это снижает стоимость и сроки фронтенда.

13. Этапы и приоритеты

MVP (этап 1): авторизация + RBAC; заявки (сайт → воронка менеджера → уведомления); контент-управление; доступность/SEO; перенос публичного сайта. *Ориентир: 4–6 недель.*

Этап 2 — монетизация: счета/оплата (эквайринг + ГИС ГМП), платная библиотека с защищённой выдачей, отчёты бухгалтерии (КОСГУ 130, данные для 0503737), выгрузка в 1С. *Ориентир: 4–6 недель.*

Этап 3 — лаборатория и ИИ: кабинеты лаборатории/научных сотрудников + протоколы + КТ-модуль; ИИ-консультант (LLM + RAG); праздничный модуль; журнал аудита; интеграция с CRM. *Ориентир: 4–6 недель.*

*Оценки ориентировочные, уточняются после согласования объёма и выбора подрядчика.*

14. Критерии приёмки

  • Все сценарии разделов 4–5 работают на реальных данных; нет «заглушек».
  • Оплата проходит end-to-end с зачислением и формированием документов; платные файлы недоступны без оплаты.
  • Отчёты бухгалтерии формируются и выгружаются (CSV/1С/данные для 0503737).
  • RBAC: каждая роль видит только разрешённое; журнал аудита фиксирует действия.
  • 152-ФЗ, ГОСТ Р 52872, WCAG AA подтверждены проверкой.
  • Нагрузочное и базовое security-тестирование пройдены; настроены бэкапы и мониторинг.

15. Что предоставляет институт

  • Юридические реквизиты: ИНН, ОГРН, банковские/казначейские реквизиты.
  • Прайс-лист услуг, обучения и изданий; файлы библиотеки и обложки.
  • Реальные кейсы, фотографии, область аккредитации испытательного центра.
  • Договоры: с платёжным провайдером, с LLM-провайдером (Yandex/Сбер), с хостингом в РФ.
  • Доступ к 1С/бухгалтерии для согласования выгрузок; контакт ответственного за ПДн.
  • Согласование политики обработки ПДн с юристом.
Платёжные ключи, доступы и денежные операции оформляет институт. Разработчик реализует интеграции, но не подключает платёжные средства и не проводит операции от имени института.

16. Открытые вопросы и риски

  • Выбор платёжного провайдера и порядок зачисления на лицевой счёт Казначейства (согласовать с бухгалтерией).
  • Закупочные процедуры (44-ФЗ) для эквайринга и подрядных работ.
  • Выбор LLM (YandexGPT vs GigaChat) и бюджет на токены.
  • Глубина интеграции с 1С (выгрузка vs двусторонний обмен).
  • Хостинг и оператор ПДн (договор, локализация).
